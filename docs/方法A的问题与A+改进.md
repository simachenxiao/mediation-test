# 方法 A 的问题与 A+ 改进

位置：`D:/产品/微表情识别/test`

本文记录 A（POS + FFT）当前的实现问题，以及 A+ 如何在不修改 `../code` 的前提下，
借鉴 B 的后处理思路做增强。A+ 不是深度学习模型，也不替代 B；它是在 A 的同一份 ROI 采样上，
用更稳的信号处理得到第二组结果。

> 当前版本 A+ 已改为 **POS-only**：不再计算 CHROM / GREEN。
> 第 8、9 节中出现的三方法候选和复测数据是历史记录，保留用于说明为什么后来收窄到 POS。

## 1. A 当前实现路径

```
播放视频
→ MediaPipe 找人脸
→ 额头/左颊/右颊固定 ROI
→ YCbCr 肤色过滤 + 平均 RGB
→ 30 秒滑动窗口，重采样到 30Hz
→ POST /physio/estimate
→ code/physio_service
   → POS 提取脉搏波
   → 线性去趋势
   → 0.7–4.0Hz 4 阶 Butterworth 带通
   → Hann 窗 + 单次 FFT
   → 0.7–4.0Hz 内取最大峰
   → bpm = 峰值频率 × 60
   → 置信度 = 峰值 ±2 bin 功率 / 频带总功率
→ 页面显示 A
```

关键参数：

| 参数 | 当前值 |
|---|---|
| 窗口 | 30 秒 |
| 采样 | 30Hz |
| 首次结果 | 约 12 秒 |
| 算法 | POS |
| 频带 | 0.7–4.0Hz |
| 滤波阶数 | 4 |
| 选峰 | 单次 FFT，取最大峰 |
| 质量 | 峰值功率占比 |
| 稳定器 | 无 |

## 2. A 的六个问题

### 2.1 0.7Hz 下边界会让慢漂移变成“42bpm”

0.7Hz × 60 = 42bpm。

带通滤波器在截止频率附近不是一刀切，而是斜坡。0.72–0.78Hz 的慢漂移仍能通过，
在频谱里形成 43–47bpm 的假峰。

A 又直接取最大峰，所以慢漂移比真实心跳强时，就会输错。

### 2.2 线性去趋势处理不了弯曲漂移

A 用：

```python
scipy.signal.detrend(x, type="linear")
```

它只减去一条直线。灯光渐变、人脸缓慢移动、自动曝光造成的弯曲基线，减不干净。

### 2.3 单次 FFT 取最大峰太武断

A 对 30 秒只做一次 FFT，然后在 0.7–4.0Hz 里取能量最大的频率。

它没有：

- 多段平均
- 第一名/第二名差距检查
- 多方法一致性检查
- 时域峰值验证

只要某个干扰峰比真实心跳峰高，就会选错；而且即使置信度很低，仍然会输出一个数字。

### 2.4 没有 SQI

A 的“置信度”只说明能量是否集中，不说明波形是否周期。

一个窄的假峰也可能有不错的峰值功率占比。

### 2.5 没有质量门控

页面在置信度低于 0.2 时只把文案改成“低质量”，数字仍然显示。

对用户来说，看到一个数字就很容易当真。

### 2.6 人脸断档被线性插值填平

人脸丢失时 A 只是停止采样；重采样阶段会把空档线性填平，产生台阶。
转头、低头之后，这种台阶会污染频谱。

另外，A 的总体 `quality` 是 HR、呼吸、SpO₂ 三个置信度的平均。
SpO₂ 置信度容易饱和到 1.0，会把总体质量抬高，不适合作为心率是否可信的唯一依据。

## 3. A+ 的设计目标

A+ 只借鉴 B 的**后处理和质量控制**，不引入 FacePhys 模型：

1. 平滑先验去趋势，替代线性去趋势
2. 频带下界 0.7 → 0.8Hz
3. POS / CHROM / GREEN 多方法
4. 额头 / 脸颊多 ROI
5. Welch 多段平均，替代单次 FFT
6. 峰值置信度 + 自相关 SQI + 第一名/第二名差距 + 方法一致性
7. 综合质量 `quality` 和可信标记 `reliable`
8. 心率稳定器：限速 + EMA + 低质量保持
9. 同时返回 `rawHr` 和 `hr`，页面可对照

A+ 不修改 `../code/physio_service`，而是新增：

```
test/aplus_service.py
```

## 4. A+ 算法步骤

### 4.1 输入

与 `/physio/estimate` 完全一致：

```json
{
  "fs": 30,
  "timestamps": [ ... ],
  "forehead": [[r,g,b], ...],
  "left_cheek": [[r,g,b], ...],
  "right_cheek": [[r,g,b], ...]
}
```

A+ 复用 A 的采样，不重复做 MediaPipe/ROI，避免两套采样时间不一致。

### 4.2 清理 RGB

去掉 `null` 和非有限值，得到有效的 `(n, 3)` 数组。

### 4.3 构造 ROI

- `forehead`
- `cheeks`：左颊和右颊按共同长度取平均

每个 ROI 独立参与候选。

### 4.4 脉搏提取方法（当前：POS-only）

当前版本只使用 POS：

```text
s1 = G - B
s2 = -2R + G + B
alpha = std(s1) / std(s2)
s = s1 + alpha * s2
```

CHROM / GREEN 已从 A+ 侧车移除。保留双频带、双 ROI、Welch、SQI 和稳定器，
但不再用三种方法做交叉验证。

> 历史版本曾使用 POS / CHROM / GREEN 三方法；由于三者在手部运动/光照变化时高度相关，
> “三方法共识”会制造虚假支持，后来收窄为 POS。

### 4.5 平滑先验去趋势

参考 open-rppg 的 `detrend()`：

```
用二阶差分矩阵做平滑惩罚
估计一条平滑基线
从信号中减掉基线
```

它允许基线弯曲，比直线去趋势更能处理灯光/运动慢漂移。

### 4.6 带通

A+ 现在使用双频带候选：

```
std: 0.8–3.5Hz
low: 0.6–3.5Hz
```

- `std` 用于避开 0.7Hz 慢漂移，覆盖约 48–210bpm
- `low` 用于保留 36–48bpm 的基频，避免 45bpm 被二次谐波顶成 90bpm
- 两个频带的候选一起参与“共识簇”选择
- 平滑去趋势的截止也随频带调整：std 用 0.8，low 用 0.6

### 4.7 Welch 功率谱

对每个候选：

```
nperseg ≈ 8 秒
noverlap ≈ 4 秒
nfft = 4096
Hann 窗
```

多段平均后，在 0.8–3.5Hz 内找峰，并用抛物线插值细化频率。

### 4.8 三个质量指标

- `confidence`：峰值附近功率 / 频带总功率
- `sqi`：自相关质量，0.5–3Hz 延迟范围内最大自相关峰
- `margin`：主峰 / 离开主峰 ±0.2Hz 后的第二名

`margin` 用来防止“两个峰差不多高，却随便选了一个”。

### 4.9 候选一致性

每个候选得到：

```json
{
  "roi": "forehead",
  "method": "POS",
  "hr": 78.2,
  "confidence": 0.21,
  "sqi": 0.42,
  "margin": 1.8,
  "score": 0.48
}
```

选择 `score` 最高的候选作为基准；把与它相差 ≤ 8bpm 的候选视为“同意”。

- 至少两个候选同意：用加权中位数作为 `rawHr`
- 只有一个候选：用它，但降低一致性得分

### 4.10 综合质量

```text
base = 0.45*confidence + 0.35*sqi + 0.20*marginScore
quality = base * (0.70 + 0.30*agreement)
```

`reliable` 条件（P0 修复后）：

```text
supportMethods >= 2          # 至少两个不同方法支持
不是“边缘单方法峰”
quality >= 0.30
sqi >= 0.22
margin >= 1.10
```

这些阈值仍然是工程初值，需要用带真值的数据校准。

### 4.11 稳定器

```text
原始值不在 30–220bpm：拒绝
第一次且 quality < 0.28：继续预热
quality < 0.22：保持上一个值，状态 holding
正常：每秒最多变化 6bpm，再做 EMA
```

返回：

- `rawHr`：未平滑的原始值
- `hr`：稳定后的值
- `status`：`warming` / `live` / `holding`
- `reliable`：质量是否达到可信条件

页面同时显示稳定值和原始值，避免“只看到平滑后的数字”。

## 5. A+ 与 A、B 的定位

| | A | A+ | B |
|---|---|---|---|
| 核心 | POS + 单次 FFT | POS/CHROM/GREEN + Welch + SQI | FacePhys.rlap |
| 输入 | ROI 平均 RGB | 同一份 ROI 平均 RGB | 人脸 36×36 图像 |
| 去趋势 | 线性 | 平滑先验 | 平滑先验 |
| 频带 | 0.7–4.0Hz | 0.8–3.5Hz + 0.6–3.5Hz | 0.5–3.0Hz |
| 选峰 | 单次最大峰 | Welch + 多方法共识 | Welch + 模型 BVP |
| 质量 | 峰值功率占比 | confidence + SQI + margin + agreement | SQI |
| 平滑 | 无 | 限速 + EMA | 限速 + EMA |
| 首次结果 | 约 8s | 约 12s | 约 30s |
| 计算 | 轻 | 轻 | 重（JAX） |
| 可解释性 | 高 | 高 | 低 |

A+ 的定位是：

> **保留 A 的轻量、可解释和实时性，同时把 B 的“清洗、选峰、质量门控、平滑”补上。**

## 7. 已知限制

A+ 仍然是摄像头 rPPG，不是医疗设备：

- 对运动、背光、肤色、戴眼镜仍然敏感
- 0.8Hz 下界意味着默认不支持低于 48bpm 的心率
- SQI / margin / quality 阈值是工程初值，不是临床标准
- 额头和脸颊平均颜色仍然会丢失空间信息
- 没有接触式 ECG/血氧仪真值，不能宣称准确率

后续如果要严谨验证，需要：

1. 同步采集视频和接触式 ECG/血氧仪
2. 对齐时间轴
3. 计算 MAE、RMSE、Bland–Altman
4. 分肤色、光照、运动、眼镜、年龄统计
5. 报告“有效输出率”，而不只是平均误差

## 8. A+ 实测发现的问题（P0 修复前）

以下是 P0 修复前的 A+ 代码实测结果，不是推测。修复后的复测见第 9 节。

### 8.1 真实视频：A+ 稳定值不错，但 `reliable` 几乎永远为 false

测试视频：`测试视频.mp4`，43.5 秒。

A+ 共返回 18 次结果：

- 大部分时间 `rawHr` 在 **75.9–78bpm**
- 稳定值 `hr` 基本保持在 **76.3bpm**
- 但 `quality` 只有 **0.13–0.33**
- 18 次里 **0 次** `reliable = true`
- 页面因此一直显示“低质量/保持”，尽管稳定值看起来合理

这说明当前 `quality` / `reliable` 阈值没有校准好：  
**A+ 的数值可能不差，但质量指标过于悲观，用户无法从 UI 判断它其实已经稳定。**

### 8.2 真实视频：候选选择会被单个高分假峰带偏

在 t≈29.7s，A+ 的候选是：

```text
POS/forehead   74.5
CHROM/forehead 130.0
GREEN/forehead 77.3
POS/cheeks     76.0
CHROM/cheeks   76.6
GREEN/cheeks   97.7  ← 分数最高
```

正确簇 74.5/77.3/76.0/76.6 有 4 个候选；  
假峰 97.7 只有 1 个候选，但因为它的 `score` 最高，`rawHr` 被选成 **97.7**。

后面的 38s、40s、42s 也出现类似情况：

```text
rawHr = 86.3 / 111.1 / 111.1
hr    = 76.3（稳定器保持）
```

稳定器把错误值挡住了，但 `rawHr` 仍然跳到 111，页面同时显示 76 和 111，容易让用户困惑。

**问题本质：**

> A+ 现在是“最高分候选胜出”，不是“多数候选共识胜出”。

POS/CHROM/GREEN 在同一个 ROI 上高度相关，单个方法可能因为某个频点噪声得到高分；  
应该优先选“多个方法 / 多个 ROI 都同意”的簇，而不是单个最高分。

### 8.3 低心率会被报成 2 倍（严重）

用 30 秒合成信号测试：

- 真实心率 + 0.25 倍二次谐波 + 0.72Hz 漂移 + 噪声
- A+ 频带 0.8–3.5Hz

结果：

| 真实 HR | A+ 输出 |
|---|---|
| 42 | 84 |
| 45 | 90 |
| 48 | 96 |
| 50 | 100 |
| 52 | 104 |
| 54 | 108 |
| 55 | 55 ✅ |
| 60 | 60 ✅ |
| 75 | 75 ✅ |

45bpm 和 50bpm 时，A+ 还会给出：

```text
quality ≈ 0.55
sqi ≈ 0.95
reliable = true
status = live
```

也就是：**它会把 45bpm 自信地报成 90bpm。**

原因是 0.8Hz 下界 + 平滑去趋势把低心率基频压掉，二次谐波反而成了主峰。  
A+ 目前没有“次谐波检查”，无法判断 90 是不是 45 的两倍。

这是当前 A+ 最严重的问题，比真实视频里的低质量更危险，因为它会“高质量地报错”。

### 8.4 纯漂移会被当成 48.8bpm（严重）

用只有 0.72Hz 慢漂移、没有心跳的 RGB 信号测试：

```text
A+ 输出：48.8bpm
quality：0.515
sqi：0.859
margin：869.752
reliable：true
status：live
method：GREEN
```

一个纯漂移信号，A+ 不仅输出了心率，还认为它高度可信。

原因是：

- 0.72Hz 漂移落在 0.8Hz 下边界附近
- 滤波器边缘没有完全切掉
- 纯正弦漂移的自相关 SQI 很高
- 没有其他峰，所以 margin 极大
- 当前 quality 公式把 SQI/margin 当成“好信号”，无法区分“周期漂移”和“心跳”

**A+ 需要增加：**

1. 频带边缘保护：峰值太靠近 0.8Hz 或 3.5Hz 时降权/拒绝
2. 绝对脉搏幅度/信噪比检查
3. 至少两个不同方法的共识，而不是同一方法在两个 ROI 上重复
4. 纯漂移/运动检测

### 8.5 早期窗口的 Welch 实际上只有一段

A+ 从 8 秒开始出结果，但 `nperseg = 8s`，8 秒窗口只有 **1 段** Welch。

此时“Welch 多段平均”并没有真正发生，结果仍然接近单次 FFT，容易抖动。

建议：

- 15 秒前只显示“预热”，不展示稳定值
- 或早期使用更短的 `nperseg`（例如 4–5 秒）以获得多段
- 或把 `minSpanSec` 从 8 提到 12–15 秒

### 8.6 稳定器的“保持”可能持续很久

真实视频里，A+ 从约 29.7s 开始进入 `holding`，一直保持 **76.3bpm** 到 43.5s，  
期间 `rawHr` 出现过 97.7、86.3、111.1。

稳定器确实避免了曲线乱跳，但：

- 页面只写“保持”，没有显示“保持了多少秒”
- 用户可能把 76.3 当成当前实时值
- `rawHr` 又同时显示 111，信息互相矛盾

建议：

- 保持超过 3–5 秒后显示 `—`，或显示“保持（12.4s 前）”
- 低质量时显示 `rawHr`，但必须标注“低质量候选”，不要伪装成稳定值
- 或者把“保持值”和“原始值”分成两个明确的字段

### 8.7 目前 A+ 的改进优先级

按风险排序：

1. **修低心率 2 倍问题**：次谐波检查 / 自适应频带 / 降低去趋势截止
2. **修纯漂移误报**：频带边缘保护 + 多方法共识 + 幅度/SNR
3. **改候选选择**：最大共识簇，而不是最高分单点
4. **校准 quality / reliable**：用真值数据重新定阈值
5. **稳定器状态透明化**：显示保持时长，低质量不突出 raw
6. **早期窗口**：15s 前不出稳定值，或缩短 Welch 段

## 9. P0 修复后的复测结果

已对 `aplus_service.py` 做了 P0 修复：

- 增加 `0.6–3.5Hz` 低频带候选
- POS/CHROM/GREEN × 额头/脸颊 × 双频带候选
- 候选按心率聚类，优先“不同方法/不同 ROI 的共识簇”
- 增加次谐波检查（主簇约为另一簇 2 倍时，优先有共识的低簇）
- 增加边缘峰保护
- `reliable` 要求至少两个不同方法支持

### 9.1 P0 修复后的真实视频复测（另一轮）

同一段视频再跑一轮，A+ 的表现和上一轮不同：

```text
t=14.0  raw=68.2   quality=0.172  reliable=false
t=18.1  raw=129.1  quality=0.158  reliable=false
t=22.1  raw=50.1   quality=0.224  reliable=false
t=30.3  raw=52.8   quality=0.217  reliable=false
t=40.6  raw=95.3   quality=0.163  reliable=false
```

这一轮 A+ 始终没有达到 `reliable`。按最新页面策略，低质量时仍会显示候选值，但会标注：

```text
A+  68bpm
状态：低质量（预热候选）
质量：17%
原始 HR：68.2bpm
```

如果稳定器已经有一个可信旧值，则显示：

```text
A+  76bpm
状态：低质量·保持（8s 前）
```

同时：

```text
A  ≈ 59bpm
B  ≈ 74bpm
```

说明：

1. P0 修复后，A+ 不会再把低质量候选硬显示成稳定值，这是进步。
2. 但这段视频的 A+ 候选本身波动很大（68/129/50/95），说明当前 ROI/信号质量仍然不够。
3. 候选簇里有时 77bpm 的簇是对的，但 130bpm 的簇因为“跨两个 ROI”排名更高；当前共识规则仍不够稳。
4. 不同轮次之间 A+ 差异明显，说明它还没有达到“可重复”的程度。

因此，A+ 目前应继续定位为**实验性对比引擎**，不能因为某一轮接近 B 就认为它已经可靠。

### 9.2 为什么低质量时仍然显示值

这是产品层面的取舍：

- 隐藏数字更安全，但用户看不到趋势，也无法判断 A+ 在做什么
- 显示数字并明确标注“低质量”，更利于对比
- 页面不使用颜色伪装成“实时可信”；低质量会显示质量百分比、SQI、原始 HR 和保持时长
- 如果用户只需要可信值，应只看 `reliable=true` 或看 `低质量·保持` 的保持时长

### 9.3 为什么 A+ 的心率常比 B 低

两者不是同一条信号链：

- A+：额头/脸颊平均颜色 → POS/CHROM/GREEN → 去趋势/带通 → Welch → 共识簇
- B：整脸 36×36 → FacePhys.rlap → BVP → Welch → SQI → 稳定器

差异来源：

1. **信号来源不同**：颜色 ROI vs 模型学出的 BVP
2. **谐波处理不同**：A+ 有次谐波检查，可能主动选低一半；B 的 `get_hr()` 直接取 Welch 最大峰，没有次谐波校正
3. **频带不同**：A+ 0.6–3.5 / 0.8–3.5；B 0.5–3.0
4. **候选选择不同**：A+ 选共识簇 + 上一轮稳定值先验；B 是模型 BVP 后处理
5. **窗口不同**：A+ 约 12s 开始，B 约 30s 后显示

所以在 70–90bpm 区间，A+ 比 B 低 5–8bpm 很常见。  
没有接触式 ECG 真值时，不能简单说“谁更低谁更准”。

### 9.4 为什么前 30 秒波动大

1. A+ 从约 12 秒开始，Welch 的 `nperseg=8s`，早期只有 1–2 段，平均效果不足
2. 前 30 秒人脸框、曝光、ROI 还在稳定
3. 候选簇在 68/77/105/130 等多个峰之间摇摆
4. A+ 没有可信旧值时，没有“上一轮先验”
5. B 在 30 秒前根本不显示稳定值，所以看起来更稳；A+ 更早显示，自然更“跳”

这也解释了为什么 A+ 早期看起来比 B 差：一部分是算法，一部分是**显示策略不同**。

## 11. 确定性重放模式（`/replay`）

实时页的结果会受浏览器播放采样影响，所以新增了独立的确定性重放页：

```text
http://localhost:3200/replay
```

### 11.1 固定了什么

| 项目 | 实时页 `/live` | 确定性重放 `/replay` |
|---|---|---|
| 采样 | `requestVideoFrameCallback`，按播放时机 | 固定 15fps 逐点 `seek` |
| 时间戳 | 浏览器当前时间，略有抖动 | 固定 `i / 15` |
| 人脸框 | 异步检测，框复用 1.5s | 固定帧序列检测，缓存复用 |
| 窗口 | 请求时刻决定 | 固定 30s 窗口，固定 1s 检查点 |
| A+ / B 稳定器 | `time.monotonic()` / `time.time()` | `replayTime` = 视频时间 |
| 重复验证 | 无 | A/A+ 自动复跑；B 可再跑一次对比 |

### 11.2 复跑结果

测试文件：`测试视频_cfr30.mp4`，1920×1080，30fps CFR，43.63s。

#### 20 秒模式（A/A+）

```text
payload Hash 一致：13/13
A 复跑一致：13/13
A+ 复跑一致：9/9
```

#### 35 秒模式（A/A+/B）

```text
payload Hash 一致：28/28
A 复跑一致：28/28
A+ 复跑一致：24/24
B 首次：77.4bpm，SQI 0.332
```

#### 33 秒模式，点“再跑一次并对比”（A/A+/B）

```text
payload Hash 一致：26/26
A 复跑一致：26/26
A+ 复跑一致：22/22
B 两次固定重放逐点一致：4/4
```

### 11.3 结论

- A+ 的信号处理和稳定器在固定 payload + 固定视频时间下是**可重复**的。
- B 在同一批固定帧、固定时间戳、reset 后重放，也可以逐点一致。
- 但“可重复”不等于“准确”：
  - 这一轮 A 约 58bpm、A+ 约 91bpm、B 约 77bpm；
  - 三者仍然不一致，说明它们在看不同的信号/峰；
  - 没有 ECG 真值，不能仅凭重放一致判断谁正确。

### 11.4 实现位置

```text

public/replay.js
aplus_service.py   # Stabilizer.update(..., now=replayTime)
deep_service.py    # Stabilizer.update(..., now=replayTime)；POST /result 支持 waitUntil
server.mjs         # /replay 路由；/deep/result POST 代理
```

`../code` 未修改。

## 12. POS-only 改造（当前版本）

### 12.1 改动

- `METHODS` 只保留 `POS`
- 删除 `_chrom` / `_green`
- 候选数从 12 变成 4：
  ```text
  2 ROI × POS × 2 频带
  ```
- `supportMethods` 恒为 1，不再用于可靠判定
- `agreement` 改为 `supportRois / 2`
- `reliable` 改为：
  ```python
  support_rois >= 2
  and not edge
  and near_conf >= 0.01
  and quality >= 0.30
  and near_sqi >= 0.22
  and near_margin >= 1.10
  ```
- 次谐波检查从 `supportMethods >= 2` 改为 `supportRois >= 2`
- 簇排序中 ROI 权重从 0.5 提到 0.75

### 12.2 结果

合成信号：

```text
42 → 42
48 → 48
50 → 50
55 → 55
75 → 75
90 → 90
120 → 120
45 → 47.9（轻微偏差）
```

`测试视频_cfr30.mp4` 40 秒固定重放：

```text
A/A+ 复跑：payload 33/33，A 33/33，A+ 29/29
A+ 全程 reliable = false
confidence 约 0.003–0.005
quality 约 0.1–0.2
页面显示低质量候选，最终约 93bpm
```

这说明：

- 删掉 CHROM/GREEN 后，A+ 不再出现“3 方法+2 ROI 同时支持 91”的虚假共识；
- 但这段视频本身质量太低，POS-only 达不到 `confidence >= 0.01`，所以 A+ 变得更保守，**始终不进入 reliable**；
- 它不会再把 91 锁成稳定值，但会显示低质量候选 93/78/162 等，仍需结合质量看。

### 12.3 结论

POS-only 是可行的，但代价是：

1. 失去 CHROM/GREEN 的交叉验证；
2. 低质量视频上可靠结果会明显变少；
3. 必须依赖 POS 自身的 confidence、SQI、margin 和运动门控。

如果希望在低质量视频上仍能出 reliable，需要进一步做：
- ROI 运动/遮挡检测；
- 更细的 confidence/SQI 阈值标定；
- 允许单 ROI 在置信度很高时通过；
- 用接触式 ECG 真值校准，而不是只凭这段视频调阈值。
